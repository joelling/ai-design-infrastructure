# Information Architecture

> **Tier 2 — Definition** | Mode: `design-ia`

## Why this matters

IA is where abstract user needs become concrete structure. It answers: what screens does this product need, how do users navigate between them, and how is content organized within each screen? This is the **direct bridge to Figma** — the screen inventory becomes the Figma page list, the content hierarchy becomes the component checklist.

This is also the first mode where technology decisions intentionally start appearing. IA bridges the agnostic upstream with the concrete downstream.

## The mental model

Think of yourself as an architect drawing the floor plan before any interior design begins. You're deciding: how many rooms, what's each room for, how do people move between rooms, and what goes in each room (at a category level, not furniture level).

The key question for every screen: "Why does this screen exist, and which personas need it for which stories?"

## Inputs

- `design/03_JOURNEYS/task-flows/*` — task flows reveal what screens are needed
- `design/05_STORIES/story-map.md` — stories define what each screen must support

## Process

**0. Check upstream sync.** Run the upstream sync check described above. If this is a first run, note which upstream artifacts are available and which are absent.

**1. Build the screen inventory.** From task flows and story maps, identify every distinct screen or view. Use the entry format below for each screen. Distinguish type using the classification guide.

**Screen inventory entry format** (one entry per screen in `sitemap.md`):

```
## [Screen Name]
**ID:** SCR-NNN
**Route / path:** /example/path  (omit for overlays and views that share a parent route)
**Type:** full screen | view | modal | drawer
**Purpose:** One sentence describing why this screen exists.
**Primary personas:** [Persona Name], [Persona Name]
**Stories served:** DS-NNN, DS-NNN
**Entry points:** [How users navigate here — e.g., "Global nav > Reports", "Action button on SCR-004"]
**Role restrictions:** [Role names] — or "All roles"
```

**Screen type classification guide:**

| Type | Definition | Use when |
|------|-----------|---------|
| Full screen | Owns its own URL route; appears in global or local navigation | The destination warrants a dedicated URL and back-navigation |
| View | A distinct visual state within a screen (tab panel, sidebar panel) — shares the parent route | Content is too tightly coupled to warrant a separate URL |
| Modal | Blocks the underlying screen; requires explicit dismiss (button, Escape key) | Confirmations, focused tasks, or forms that don't warrant a full page |
| Drawer | Slides in from edge; partial overlay; underlying screen still partially visible | Detail expansion, secondary task panels, filter panes |

When in doubt: if a user would expect the browser Back button to take them to the previous screen, it's a full screen. If Back would feel wrong, it's a view or overlay.

**2. Design the navigation model.** Define global navigation (always visible) and local navigation (contextual). Document in `navigation-model.md` using this structure:

**Global navigation entries** (items always accessible regardless of current screen):
```
| Label | Icon (if applicable) | Route | Roles visible to | Order |
```

**Local navigation entries** (contextual within a screen or section):
```
| Label | Type (tab / sidebar / breadcrumb) | Parent screen (SCR-NNN) | Roles visible to |
```

Consider: can the product be entered from multiple places (deep links, notifications, external redirects)? Document each entry point and its landing screen.

**Note:** the role-feature access matrix is **not** maintained in `navigation-model.md` — it lives in `rbac.md` (step 2b). `navigation-model.md` keeps only the per-entry "Roles visible to" column and a back-reference to `rbac.md`.

**2b. Build the RBAC matrix.** In `rbac.md`, capture the canonical role-feature access matrix that downstream modes and the BRD consume:

```
| Role | Feature / Capability | Access (read / write / admin / none) | Screen IDs (SCR-NNN) | Notes |
```

The matrix is the source of truth for role permissions. `navigation-model.md` derives its "Roles visible to" entries from this matrix. The BRD RBAC sheet is generated from this file by `sync-brd.py`.

**3. Map content hierarchy.** For each screen, define what information appears in three levels: primary (immediately visible), secondary (visible on scroll or interaction), and tertiary (available on demand). List available actions and who can perform them.

**3b. Build the data dictionary.** In `data-dictionary.md`, normalise the per-screen field lists from `content-inventory.md` into a global catalog:

```
| Field ID | Field name | Type | Validation | Format | Source screens (SCR-NNN) | Notes |
```

Every field that appears in any screen's content inventory must have a row here. Source-screen back-references make it possible to find every screen that surfaces a field. The BRD Data Fields sheet is generated from this file by `sync-brd.py`.

**4. Define the taxonomy.** How is content categorized and labeled across the product? Content types, categorization scheme, label conventions.

**5. Compile the notification catalog.** In `notifications.md`, list every notification message the product emits. Notifications are messaging artifacts (text + channel + recipient + trigger), not interaction logic — interaction triggers live in `07_INTERACTION/`, but the message text itself is canonical here.

```
| NOTIF ID | Channel (in-app / email / push / SMS) | Recipient role | Copy template | Trigger event | Variables | Notes |
```

Downstream artifacts reference notifications by `[NOTIF-NNN]` tag — `error-strategy.md` and `behavioral-spec.md` link to the NOTIF id rather than carrying the message text inline. The BRD Notification Mapping sheet is generated from this file by `sync-brd.py`.

## Rules

- Every screen must trace back to at least one user story or task flow. No orphan screens.
- **Stories served is mandatory.** Every screen entry in `screen-inventory.md` MUST include a `Stories served:` field listing DS-NNN IDs. This is the authoritative junction table for story-to-screen mapping — canvas briefs and the traceability script consume it.
- Navigation must account for all roles — document variations explicitly.
- Content hierarchy uses three levels: primary, secondary, tertiary. Don't flatten everything.
- Screen names established here become canonical — used everywhere downstream in Figma pages, canvas briefs, and component names. Choose them carefully.

## BRD aggregation

The IA artifacts are the canonical source for four BRD sheets — `sync-brd.py` reads them directly. There is no manual enrichment step:

| BRD sheet | Source md | How sync-brd.py uses it |
|---|---|---|
| User Stories — Feature/Touchpoint (col C) | `sitemap.md` | Reverse lookup: for each DS-NNN, find screens whose `Stories served` includes that ID |
| RBAC | `rbac.md` | Direct table copy of the role-feature matrix |
| Data Fields | `data-dictionary.md` | Direct table copy of the field catalog |
| Notification Mapping | `notifications.md` | Direct table copy of the NOTIF-NNN catalog |

Run `python design/scripts/sync-brd.py` after any IA update to regenerate the BRD. If `navigation-model.md` still contains a role-feature matrix from a legacy version, `sync-brd.py` warns and prefers `rbac.md`.
